# Dashboard

The React dashboard in `apps/dashboard` follows the check-centered [information architecture](../product/information-architecture.md). It talks only to the same-origin `/v1/admin` API. Admin cookies stay HttpOnly; the session-bound CSRF token stays in memory and accompanies mutations. Credentials are never passed in URLs.

## Development

Run `pnpm --filter @krine/dashboard dev`. Vite listens on `127.0.0.1:5174` and proxies `/v1` to `127.0.0.1:8080`, preserving the browser Origin. Configure `KRINE_ADMIN_ORIGIN=http://127.0.0.1:5174` on the development backend. The explicit port fails if occupied. Production hosting must serve the built application and API under the configured admin origin, with a history fallback for dashboard routes.

`pnpm --filter @krine/dashboard build` typechecks and builds static assets; `pnpm --filter @krine/dashboard test` runs the editor, transport and persistence tests. The app uses system fonts and no remote assets.

## Draft and publication safety

A check has one shared revisioned draft. Autosave serializes mutations and preserves the exact body and idempotency key after an ambiguous transport/server failure. Edits made during a save remain local until the earlier result is recovered, then use its acknowledged revision. A definitive conflict requires a comparison with the latest shared draft and an explicit choice of which complete definition to keep. The backend performs the final atomic revision check.

Unsaved policy and description state, including unresolved save, publish and restore intent, have a recovery copy in this tab’s session storage. Recovery validates each check-specific intent. The operator must deliberately retry its original body and key; reopening a page or signing in never resubmits it. Authentication failures, throttling, timeouts and malformed acknowledgements retain that intent: they cannot establish whether an earlier submission committed. Successful check/version responses are validated before recovery is cleared. A reopened editor owns the recovery record; responses to detached editors cannot erase it. Publication preserves newer local work, and restoration replaces only fields unchanged since its confirmation. Storage failure is visible; navigation warns while work remains unsaved, and page unload also warns about unresolved mutation intent. A 401 opens same-operator sign-in without unmounting the editor. A 403 distinguishes insufficient permission from CSRF verification and refreshes session metadata without repeatedly requesting credentials. Neither a denial nor an actor-changed 409 proves an earlier ambiguous effect failed. The original intent retains its original installation and actor, even after reauthentication. A failed save disables publication.

Publication reviews rule order, conditions, metric versions, unknown routes, trusted input declarations and the final outcome. Its mutation includes both the reviewed draft revision and active version. Lost responses retry the same mutation. Restoration explicitly replaces a draft; it never activates a historical definition directly. Historical policy and metric links fetch the exact version.

Activity filters and pagination live in the URL. Investigation links carry that scope through related records, checks, entities and metrics; returning restores the list position. Refresh is explicit so investigation rows stay still. Failed refreshes mark retained rows as stale and show their last successful refresh time. Decision explanations lead with decisive captured values or unknown causes. Otherwise outcomes explain why rules continued, with a bounded leading summary and the complete policy path in a disclosure. Provider contribution and ordered verification steps use the attempt's captured evidence; a passed verification step never implies final authorization. Entity pages show applicable current observations separately. Exact UTC timestamps with milliseconds appear on keyboard focus or hover. Entity relationship lists are paginated and do not imply identity merges.

## Application credentials

Application connection contains a compact, expandable credential list. Creation distinguishes public browser keys from server secrets. A server secret stays only in the creation result’s memory until dismissed; it never enters browser storage, logs, URLs or SDK reference snippets. Copying requires an explicit action. Revocation reviews the exact credential and warns when the latest connection status reports it as the last active key of its class. Lists retain revocation metadata and refresh together with connection status after mutations. Confirmed revocation remains authoritative for that ID throughout the mounted form’s lifetime, across page changes and stale reads; a delayed creation response cannot reveal or offer to copy a known-revoked secret. Connection responses are validated before replacing the last valid setup; an invalid refresh shows a read error and preserves the mounted credential form, including its sole secret or unresolved request. An invalid initial response provides Retry instead of an empty connection section.

An unconfirmed create or revoke preserves its exact non-secret body and idempotency key in this tab’s session storage. Recovery validates the endpoint and body before use, preserves intent through authentication interruption and malformed responses, and refuses retries after 23 hours, within the backend’s 24-hour retention contract. A lost creation response can recover metadata but cannot recover the server secret; the interface offers explicit revocation and replacement. Storage failure is visible and retains an in-memory retry. Detached responses cannot clear a reopened form’s recovery record. Settings uses one navigation guard for both credentials and providers; page unload warns while a request is unconfirmed or a newly revealed secret remains open.

The SDK reference handles a deployment with no active browser key explicitly. HTTP development URLs include `allowInsecureHttp: true`; HTTPS examples retain strict transport defaults. Evidence that must affect a protected action uses proof-bound context resolution before the check. Continuous events can instead resolve the browser’s opaque context credentials.

## Provider configuration

Settings keeps one expandable row per capability, with SDK reference material collapsed. A candidate must pass its supported test before explicit review and save. Both a usable partial IP lookup and Turnstile's limited format check can return `configuration_checked`; the interface preserves the explanation and does not claim live key pairing. Editing a candidate invalidates its test. Configuration changes show the exact affected published policy versions and their unknown/verification paths. Save carries the backend's dependency token, so a concurrent publication requires another review.

Candidate secrets, activation tokens and an unresolved save's exact request live only in the mounted form's memory, never in browser storage or URLs. An empty secret field retains the stored key; explicit removal is available for proxycheck's optional key. Ambiguous saves freeze the candidate and retry the original body and idempotency key, including across reauthentication and malformed responses. Only a validated acknowledgement clears this intent. A successful replay is followed by a current-state read before the interface calls the configuration current. Stale revisions require explicit reconciliation and a new test. A failed current-state read blocks further edits until refreshed.

Navigation, including Settings tabs and browser history, warns before discarding entered values and stays on an unconfirmed save until its result is recovered. Filters within Application keep the mounted forms. Reloading or closing the tab warns but cannot preserve secret-bearing retries: reopen Settings to inspect the current masked configuration before making another change. Verification settings links carry the originating check and return to its draft; the existing policy recovery mechanism remains independent.

## Individual operators

Settings contains Application, Your sessions, Operators and Audit, according to current capabilities. Viewers investigate, Editors also author policies and correct relationships, and Admins manage providers, application credentials, operators and audit. Recovery displays its reason and expiry and mounts only operator repair; it does not fetch customer configuration or history. Own-session revocation uses the revision in the current session, so a Viewer does not need permission to read operator administration.

Bootstrap and named sign-in follow the [operator protocol](protocol.md#individual-operator-access). Bootstrap and operator creation or rotation reveal a generated credential once, only in memory. Save it in a password manager before continuing. A lost reveal cannot be retried to obtain the secret again; use deliberate rotation or host recovery. Self-rotation ends the session; its confirmed reveal remains available while the operator saves it before signing in again.

All authenticated mutation intents capture the installation and actor at creation. Their actor header is never replaced by the currently signed-in person. Browser recovery records are namespaced by that pair. Older unbound records remain untouched with a recovery notice; the dashboard does not adopt or replay them. Different-operator sign-in, installation change and capability change unmount prior views and invalidate late requests. Same-operator reauthentication retains legitimate unsaved work without automatic submission. Cross-tab notifications contain no credentials; they trigger a fresh server session read. Focus, periodic refresh and the session expiry deadline also recheck access. Server authorization remains authoritative for every read, mutation and replay.

Operator lifecycle forms carry the reviewed revision and a reason. Role changes, disablement and credential rotation explain their session effects before confirmation. Internal navigation stays with an in-flight or unconfirmed request, including a restored intent or a session revocation with no editable form. A generic discard action cannot abandon that request; an expired retry requires inspecting its outcome before acknowledgement. Confirmed revocations override delayed older session reads. Administrative audit has its own coverage boundary and retention; it renders attributable, secret-safe changes rather than raw requests. The dashboard does not claim that legacy shared-operator activity has a known individual actor.

Captured publication, provider, credential and relationship details retain their actor independently of the general audit window. These views show the captured name and stable ID without resolving mutable operator metadata. Host configuration, host recovery, legacy shared administrators and missing attribution remain distinct.
